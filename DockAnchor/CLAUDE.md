# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Persona & Constraints
- Reply with minimal filler. Start directly with the requested output, code, or bullet points.
- Use bullet points for explanations and plans.
- Output raw code or complete file updates when necessary.
- Suppress internal reasoning or chain-of-thought outputs unless explicitly requested.
- If a task is ambiguous, ask clarifying questions before proceeding.
- Do not explain what you're about to do — just do it.
- Do not summarise what you just did after completing a task — end on the last line of output.
- Never re-explain context I've already provided — if I paste code or a tree, use it directly without narrating what you see.
- Never output more than 2 sentences of prose before code or a question.
- If you find yourself weighing options in output, stop — ask instead.

## Architecture & Codebase
- Maintain and update a high-level `architecture.md` as the system evolves. Create it if it doesn't exist.
- At project start, if `.claudeignore` doesn't exist, generate one based on the declared Tech Stack and save it automatically. If Tech Stack is not filled in, ask before generating.
- If you encounter a file during a task that is irrelevant to the current and future tasks, suggest adding it to `.claudeignore` and wait for confirmation before doing so.
- At the start of each session, read `file-tree.md` if it exists. It is auto-generated by the SessionStart hook.
- When analyzing the codebase, refer to `file-tree.md` and `architecture.md` only. Never scan or read files to understand project structure.
- Never re-derive system design, patterns, or data flow — read `architecture.md` first. If the answer isn't there, ask me before inferring.
- Before reading any file, check if its contents are already in context — do not re-read.
- Only modify files directly relevant to the current task. If you notice a bug outside scope, flag it but don't fix it.

## Code Standards
- Always write modularized code with a separation of concerns approach.
- Follow Test Driven Development best practices.
- If a code block exceeds 50 lines, check if it can be split into smaller functions or modules before outputting.
- Plan the structure of any code block before writing it — do not write then refactor in the same response.
- Before declaring a new type or importing a utility, check existing types and imports in the codebase first.
- Do not re-output unchanged file sections — use `// ... rest unchanged` for unmodified blocks.

## Logging Conventions
- Print format: `[FileName:functionName] relevant content` — e.g. `[DockRelocationService:detectCurrentDockState]`.
- Never print raw display IDs (`CGDirectDisplayID`) or UUIDs in logs — always resolve to the display's `.name` property.
- Never print raw `CGRect` frames in informational logs — extract only the values relevant to the message.

## Planning
- Use the `/planning` skill for all feature and task planning.
- Do not start implementation until I explicitly approve the plan.
- For each distinct plan, save it to a new document in the `Plans/` directory once approved by me. Name the file descriptively after the feature or task (e.g. `Plans/auth-refresh-token.md`).
- When implementing a planned phase:
    - Execute directly. Do not deliberate or explore alternatives internally.
    - If you encounter ambiguity, a blocker, or a decision not covered by the plan, STOP immediately and ask before proceeding.
    - Never produce exploratory reasoning as output. Act or ask — nothing in between.
- When implementing, output code or a BLOCKED message only. No prose reasoning, no alternatives, no deliberation.
- BLOCKED format: "BLOCKED: [one sentence]. What should I do?"

## Debugging
- State your hypothesis in one line, then output the fix — no further explanation unless asked.
- Do not apply multiple speculative fixes at once.
- When reporting an error, output the error type and location only — no stack trace narration unless asked.

## Agents
- When spawning subagents, select the model based on task complexity:
    - Use `claude-haiku-4-5` for: single-file edits, boilerplate generation, test generation for simple functions, find-and-replace style changes
    - Use `claude-sonnet-4-6` for: multi-file changes, debugging, complex logic, anything requiring cross-file awareness
    - Default to Sonnet if uncertain
- When spawning a subagent, always pass `file-tree.md` and `architecture.md` as part of the subagent's initial context.
- Regenerate `file-tree.md` before spawning a subagent if files have been created or modified in the current session.
- If a task contains 2 or more independent steps that write to different files, automatically spawn parallel subagents rather than executing sequentially.
- Never parallelise steps that write to the same file — these must remain sequential.

## Session & Token Management
- Proactively suggest `/compact` at natural task boundaries — after a feature is complete, before starting a new task, or when conversation history is long. Flag it with: "Good checkpoint to run `/compact` if context is getting long." Prioritize code samples and API details during compaction.
- If context is above 50%, prompt me to run `/compact` immediately.

## Tech Stack
- Language: Swift 5.x
- Framework: SwiftUI + AppKit/Cocoa (macOS only)
- Package manager: None (native Xcode, no SPM/CocoaPods)
- Test runner: XCTest (unit: `DockAnchorTests`, UI: `DockAnchorUITests`)
- Linter / Formatter: None
- Persistence: UserDefaults (settings + profiles), Core Data (scaffolded, currently unused)
- System APIs: CoreGraphics, ApplicationServices (AXUIElement), CGEvent tap, NSAppleScript, ServiceManagement (login item)

## Forbidden Actions
<!-- Critical rules are enforced deterministically via .claude/settings.json hooks -->
- Never delete files or directories without explicit confirmation.
- Never commit directly to `main` or `master`.
- Never expose, log, or hardcode secrets or environment variables.
- Never install packages without confirming with me first.
- Never overwrite existing files silently — flag conflicts and ask.
